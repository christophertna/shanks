Shanks feature roadmap

Priority 1 - Maintenance and developer experience

1- Nothing proves `GitHubAdapter` satisfies the `RepositoryAdapter` protocol.
    Nodes annotate `repository: RepositoryAdapter | None` but reach
    capabilities through `getattr(repository, "<method>", None)` (`preflight`,
    `drift_report`), so a renamed or typo'd adapter method silently disables
    the feature with no failing test - and test doubles that omit methods are
    still accepted, since tests are not type-checked.
    Fix: a contract test in `tests/test_node_contracts.py` asserting every
    `RepositoryAdapter` member exists on `GitHubAdapter`. Roughly a dozen
    lines against a whole class of silent feature loss.

Priority 2 - Reliability and contributor experience

1- Read-only Git probes share the 3600-second command timeout.
    `GitHubAdapter._run` applies one `timeout_seconds` to every command. That
    budget exists for the preflight unittest suite and quality gates, but the
    quick probes share it - `git fetch`, `rev-list --count`, `status --short`,
    `branch --show-current`. `GIT_TERMINAL_PROMPT=0` rules out a
    credential-prompt hang, but a stalled HTTPS fetch during the per-item
    drift check blocks a planning node for an hour with no output. Low
    probability, high impact, cheap fix: a short per-command timeout for the
    read-only probes.

2- A missing `gitleaks`/`jq` reads as a secret-scan regression, not a missing
    tool. The Python suite now depends on both being on `PATH`:
    `test_tests_md_shell_check_counts_match_harness_output`
    (`tests/test_cli.py`) shells out to
    `hooks/test.hooks/test-secret-scan.sh`, which fails closed when either
    binary is absent, so the failure prints `expected=allow got=block` lines
    (verified with a stripped `PATH`). Fix: detect the missing tool in that
    test and fail with a message pointing at `./shanks doctor`.

3- `serve_graph.py` never registers `failed_run` in any curated viewer
    constant (`GRAPH_NODE_ORDER`, `VIEW_NODE_LABELS`, `VIEW_MAIN_NODES`,
    `VIEW_RECOVERY_NODES`), even though it is a real, frequently-reached
    terminal node (routed to from `critic_auditor`, `debugger`, `learning`,
    `planning`, `pre_commit_policy_gate`, `push_node`, and `validation`). It
    only appears in the raw/unstyled mermaid mode, never the structured view
    most people look at. Fix: add it alongside `attempt_limit`/`failed_build`
    in the recovery-node set.

Suggestions

- The repository drift note refreshes once per PRD item, in `planning` only.
  `learning` never receives it, and a long build -> critic -> validation ->
  debugger loop inside a single item works from the drift snapshot taken
  before the first build. Carries a `ponytail:` comment naming the ceiling;
  moving the refresh into `_versioned_node` would fix it at the cost of one
  `git fetch` per node call.
- `scripts/quality_gates.py`'s mypy target list only checks `adapters.py`,
  `contracts.py`, `retries.py`, and `state.py` - `nodes.py`, `lifecycle.py`,
  `workspaces.py`, `cli.py`, and `graph.py` (the largest and most stateful
  modules) are unchecked. Extend the list once those modules are clean under
  mypy, or budget time to fix what surfaces.
- No audit trail of what Ralph actually did inside a session - the run
  manifest records the launching command and the final `--print` output,
  not the individual tool calls (files read/written, Bash commands run)
  during the session. Would help post-incident review; capturing
  `--output-format stream-json` (or equivalent) into the run manifest is
  the likely shape.
- `critic_auditor` runs *before* `validation` in the graph (build -> critic
  -> validate), and `ClaudeOpus48CriticAdapter` has no `Bash` at all, so it
  can never actually run the tests it's judging - only reason from source.
  `GPT56LunaCriticAdapter` (`codex exec --sandbox read-only`) can execute
  commands read-only, so the two critics have materially different
  verification power. Worth a design discussion, not just a permissions
  tweak, before changing it.
- Add a `UserPromptSubmit` hook that injects fresh state before Claude reads
  the prompt: current branch, recent commits, open PR status, and whether
  `.venv/bin/python -m unittest discover -s tests` currently passes, so a run
  never starts blind on a broken build.
- Add a `PostToolUse` hook that runs Black/Ruff (and mypy) on the exact file
  Claude just touched and feeds failures back immediately, instead of only
  catching them later at `scripts/quality_gates.py --diff-base origin/main`.
- Split oversized workflow modules for maintainability and iteration speed.
  `workflow/adapters.py` combines agent, critic, test, GitHub, parsing, and
  security boundaries, while `workflow/nodes.py` combines orchestration,
  routing, retries, delivery, and audit helpers. When change volume justifies
  the churn, turn each into a focused package while preserving public imports
  and test coverage. This is a developer-experience optimization, not a
  runtime-performance optimization.
- The check itself is cross-platform, but `./shanks doctor`'s Git/gh version
  check only guards a stale local dev machine (macOS here); CI's
  `ubuntu-latest` always ships far newer versions, so the documented floor
  (Git 2.30, gh 2.40) is never actually exercised on Linux either. Pinning
  old Git/gh versions in CI to prove the floor works is real setup effort for
  a small payoff — defer unless a real floor-version bug shows up.
- `./shanks doctor`'s `tools` check only verifies `gitleaks`/`jq` are
  present, not their version (unlike `git`/`gh`, which have
  `_MIN_TOOL_VERSIONS`) - a `gitleaks` upgrade could silently change
  detection rules/behavior with nothing to notice. Low urgency; worth a
  version floor if a real detection regression ever traces back to a
  `gitleaks` upgrade.
- `hooks/post-merge`/`hooks/post-checkout` (#44) run `graphify update .`
  synchronously, unlike `hooks/graphify-update.sh` (the Claude Code hook),
  which backgrounds the call with a lockdir debounce. Fine today since it's
  AST-only and fast, but a `git checkout`/`git pull` that actually changes
  the tree will block on the rescan - revisit if that becomes noticeable on
  a larger codebase.
- `hooks/pre-push` (#45) hardcodes `origin/main` as the diff base rather than
  reading the remote/ref Git actually passes it (`$1`/`$2` args, plus a
  `<local ref> <local sha1> <remote ref> <remote sha1>` line per ref on
  stdin). Matches every push in this repo today (single remote named
  `origin`, default branch `main`), but a fork-based push to a different
  remote would hit a diff base that doesn't exist and fail closed - blocks
  the push instead of gating it. Low urgency while this repo has one
  contributor pushing straight to `origin`; revisit if a fork workflow shows
  up.
- `hooks/pre-push` (#45) doesn't read its stdin ref list, so a
  `git push origin --delete branch` still pays for a full
  `scripts/quality_gates.py` run (black/ruff/mypy/pip_audit) even though
  there's no new code to gate - the local sha for a deleted ref is all
  zeros, a cheap check to skip on. Minor cost today, worth trimming if
  branch-deletion pushes become frequent.
- Preserve fail-closed token, branch, reviewer, label, and subprocess policies
  as new lifecycle capabilities are added.
- Lesson from `hooks/pr-checkpoint-reminder.sh` (built, then removed this
  session): before adding a new advisory `PreToolUse`/`PostToolUse` hook as
  a "safeguard" against an agent skipping a step, check that the failure
  mode is actually a tool-call boundary. Hooks can't see whether the agent
  chose prose over calling a tool at all - only tool calls that do happen.
  That hook's whole premise didn't hold up; worth checking this before
  building the next one.
- `graph.html`'s mermaid-rendered text (`.node` labels, `.cluster-label`
  subgraph titles) lives inside an SVG `foreignObject` that mermaid sizes
  using its own default font metrics at render time - any page CSS that
  later bumps `font-weight`/`font-size` on that text (as the node-label and
  cluster-label rules both do) can make the real text wider than the box
  mermaid already committed to, and `foreignObject` clips overflow by
  default. Hit this twice this session (node labels, then cluster labels
  after the same pattern of styling change) before landing on the fix: pair
  any such CSS rule with `overflow: visible !important` and
  `max-width: none !important` on the `foreignObject` itself (see the
  `#diagram svg .node foreignObject` and `#diagram svg .cluster-label
  foreignObject` rules). Worth remembering before the next label-styling
  tweak.
- Mermaid/dagre quirk found while prototyping a (since-reverted) serpentine
  workflow layout in `serve_graph.py`: a nested subgraph declared
  `direction: RL` inside a `TB`-direction parent renders *above* its sibling
  in the vertical stack, even when it's the topological successor (i.e. the
  connecting edge points into it) - the rank order comes out inverted from
  what the edges imply. `direction: BT` in the same position didn't have
  this problem. No fix needed today since the serpentine layout was
  reverted in favor of a flat `LR` flow, but worth knowing before attempting
  another mirrored/serpentine mermaid layout so the rank-inversion isn't
  re-discovered by trial and error.

OS-specific (macOS-only mechanisms and fixes)

- `scripts/sandbox_claude.sh` only sandboxes on macOS (`sandbox-exec`); it
  falls back to unsandboxed elsewhere. There's no separate "Windows" case to
  build - the whole toolchain (ralph.sh, hooks/*.sh, ./shanks) is bash-only,
  so a Windows user is already running it under WSL2, which is Linux. This
  is really one item: Linux sandbox parity (bubblewrap or Docker, scoped to
  $TARGET_DIR the same way). No urgency today since Ralph doesn't run in CI
  and local dev here is macOS; revisit if Ralph ever runs on a Linux/WSL dev
  box or in CI.
- `scripts/sandbox_claude.sh`'s write allowlist
  (`~/.claude`/`~/.codex`/`~/.npm`/`~/.cache`) was hand-picked by probing
  `claude --version`/`codex --version` empirically, not from upstream
  documentation - a future CLI version adding a new config/cache path would
  silently reintroduce "Operation not permitted" failures that look like
  flaky runs, not a sandbox problem. Only possible on macOS today since
  that's the only OS with a sandbox at all. Consider a `./shanks doctor`
  check that runs `claude --version` (and `codex --version`) through the
  sandbox wrapper to catch that drift immediately instead of mid-run.
- No network egress control on Ralph's build agent - the denylist only
  blocks the specific `curl|sh` pattern, nothing stops `pip install
  <package>` or other outbound calls. The gap itself applies on every OS,
  but the current partial mitigation is macOS-only: `scripts/sandbox_claude.sh`
  (the filesystem sandbox) deliberately leaves `(allow network*)` in its
  Seatbelt profile, since Claude itself needs network for its own API
  calls, so this would need per-host allowlisting (Anthropic's API, not
  arbitrary destinations), not a blanket deny. On Linux there's currently no
  sandbox at all yet, so the same gap is compounded there - filesystem
  writes aren't contained either. Defer until there's a concrete need (e.g.
  running against untrusted PRD content).
- `hooks/run-impacted-tests.sh` has no timeout on the matched test run - a
  hung test (infinite loop, blocked I/O) would stall every subsequent
  Write/Edit indefinitely, since the hook runs synchronously by design (it
  needs the exit code for blocking feedback). The stall risk itself is not
  OS-specific, but the fix is harder on macOS specifically: Linux ships GNU
  coreutils' `timeout` by default, macOS does not, so a portable version
  needs a hand-rolled background-process-plus-kill pattern instead of one
  command. Not urgent today - all matched modules are fast and none hang.

Big tasks (ordered by priority)

1- Event-sourced execution history and deterministic replay.
    Replace checkpoint snapshots plus node-level `run_manifest` entries with
    an append-only execution and artifact history. Record adapter responses,
    approvals, subprocess/tool events, and enough workspace evidence to
    reproduce a run without repeating non-deterministic or side-effecting
    operations. Add replay CLI support, mocked side-effect adapters, retention,
    viewer timeline support, and local evaluation metrics.

2- PR/CI feedback loop.
    Extend the current terminal-after-pull-request flow to consume GitHub check
    results and review feedback. Wake the run through an event-driven or
    interrupt-based mechanism, classify actionable failures, route them back
    through planning/debugging, then rebuild, validate, and push with approval
    and loop limits. Do not hold a worker in a polling loop.

3- Parallel PRD-item execution and merge orchestration.
    Replace sequential item selection with bounded fan-out for independent
    items. Add per-item worktrees, scheduling, budgets and leases,
    deterministic merge/commit ordering, conflict handling, partial-failure
    recovery, and aggregate pull-request behavior. Start only after recovery
    and pull-request lifecycle behavior are reliable.

4- Linux/Docker-native version of Shanks. Today the project assumes a macOS
  dev machine end-to-end: `scripts/sandbox_claude.sh`'s filesystem
  containment only works via `sandbox-exec` (Seatbelt) and falls back to
  running the build agent completely unsandboxed on Linux (see the Linux
  sandbox parity item in OS-specific above); `./shanks doctor`'s Git/gh
  version floor is never actually exercised outside macOS; and there's no
  packaged way to run Shanks itself (not just the agent it drives) in a
  container. This is a bigger initiative than the existing sandbox-parity
  item and needs its own design pass before starting:
  - Filesystem/process containment on Linux: bubblewrap (`bwrap`) is the
    closer analog to Seatbelt (no daemon, per-invocation namespace,
    write-scoped-only semantics matching `tests/test_sandbox_claude.py`'s
    existing containment contract) versus a Docker-based approach that runs
    the whole build agent - not just its filesystem writes - inside a
    container for full process/network isolation, at the cost of needing
    Docker installed and running plus an image to build and maintain.
  - A `Dockerfile` (and maybe `docker-compose.yml`) bundling Python 3.11,
    Node (for the `claude`/`codex` CLI installs, see
    `.github/workflows/agent-smoke-tests.yml`), `git`, `gh`, `gitleaks`,
    and `jq`, with the target repo mounted as a volume, so Shanks can run
    reproducibly without a hand-set-up host machine - useful both for CI
    (the agent-smoke-tests job currently reinstalls everything from
    scratch on every manual run) and for a non-macOS contributor's first
    setup.
  - `./shanks doctor` and its `_MIN_TOOL_VERSIONS` floor should get
    actually exercised on Linux once either path exists, closing the gap
    already noted in the Suggestions section above.
  No urgency today - single macOS-based contributor, Ralph doesn't run in
  CI - but worth a deliberate design discussion (bubblewrap vs Docker,
  whether Shanks-the-orchestrator and the agent sandbox are containerized
  together or separately) before starting, not just picking whichever is
  faster to prototype.

Deferred

- Additional agent roles. Revisit after isolation, recovery, and pull-request
  lifecycle behavior are reliable.

Graph Suggestions (ordered by implementation priority)

1. Human-in-the-Loop State Injection (Next)
   Instead of simply approving or rejecting operations, allow humans to inject validated guidance during interrupts so the agent can resume with corrected instructions without restarting the chain. Do not allow arbitrary patches to safety-critical state.

2. Context Pruning/Compaction Node (Later)
   After measuring prompt growth, periodically distill past command outputs, test logs, and history into a compressed summary to control context size and token cost during long iteration cycles.

3. Namespaced State Management (Later)
   Move from the flat dictionary to structured, nested TypedDicts. Add runtime validation or update boundaries if nodes must be prevented from writing outside their namespaces.

4. documentation_sync (Later)
   Automate updates for READMEs, OpenAPI specs, and architecture diagrams based on the final code state, subject to an explicit source-of-truth policy.

5. regression_canary (Later)
    Add deterministic performance benchmarks and thresholds to detect latency or resource regressions after code changes.
