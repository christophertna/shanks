Shanks feature roadmap

Priority 1

1- Gate commits/pushes on quality_gates.py, not just CI.
    `scripts/quality_gates.py` (black/ruff/mypy/diff-size) isn't run by
    `.venv/bin/python -m unittest discover -s tests`, and nothing local
    blocks a commit or push that fails it - it only surfaces once CI runs.
    Landing #42 and #43 both hit the same black-formatting failure on push,
    caught only after opening the PR. Fix: add a `pre-push` git hook (or
    extend an existing `PreToolUse` guard on `git commit`/`git push`) that
    runs `scripts/quality_gates.py --staged` and blocks before it ever
    reaches CI.

2- Regression-test retry-policy coverage across all lease-touching nodes.
    #43 closed the gap where `TARGETED_RETRY_POLICY` wasn't attached to
    every node that calls into the SQLite-backed lease through
    `_versioned_node`, but nothing stops a newly added node from silently
    reintroducing it - the same "guard silently doesn't apply" pattern the
    `hooks/HOOKS.md`-drift suggestion below calls out for hook scoping.
    Fix: add a test asserting every key in `create_nodes()`'s dict has a
    matching `retry_policy=TARGETED_RETRY_POLICY` registration in
    `build_graph()`.

Priority 2 - Maintenance and developer experience

1- Scoped test-impact hook.
    Add a `PostToolUse` hook on `Write|Edit` that runs just the test
    module matching the touched file by naming convention (e.g.
    `workflow/workspaces.py` -> `tests.test_workspaces`), and skip the run
    when there's no direct match rather than guessing broadly at what to
    test, so regressions surface on every edit without paying for a full
    suite run each time.

2- Wire real-agent smoke tests into CI.
    Wire tests/test_agent_integration.py into an opt-in, manually-triggered
    CI job (workflow_dispatch, with the CLI auth secrets scoped to it) so
    the smoke tests - including the sandboxed Claude write path added in
    #36 - get run on a schedule instead of only ad hoc by a developer.

3- Grep/Glob for the read-only Claude adapters.
    Give the Claude-based read-only adapters (DebuggerAdapter,
    ClaudeAdapter(read_only=True), ClaudeOpus48CriticAdapter) `Grep,Glob`
    alongside `Read` in their `--tools` list - still fully read-only, same
    guarantee as today - so they can search the codebase for related
    callers/regressions instead of only inspecting files already named in
    their context.

Suggestions

- Real-agent smoke tests (tests/test_agent_integration.py) only cover the
  Codex and Claude planner/builder adapters; the GPT-5.6 Luna and Claude
  Opus 4.8 critic adapters still have no real-CLI coverage. Extend once
  there's an authenticated environment to run them in.
- Preserve fail-closed token, branch, reviewer, label, and subprocess policies
  as new lifecycle capabilities are added.
- Add a `UserPromptSubmit` hook that injects fresh state before Claude reads
  the prompt: current branch, recent commits, open PR status, and whether
  `.venv/bin/python -m unittest discover -s tests` currently passes, so a run
  never starts blind on a broken build.
- Add a `PostToolUse` hook that runs Black/Ruff (and mypy) on the exact file
  Claude just touched and feeds failures back immediately, instead of only
  catching them later at `scripts/quality_gates.py --diff-base origin/main`.
- For Ralph/graph runs (not Claude Code sessions), inject into the next agent
  prompt only state the graph doesn't already track through `WorkflowState` —
  worktree drift from outside the run, or upstream `main` moving since the run
  started — as a preflight check inside `workflow/nodes.py`, not a generic
  hook, so it stays versioned and available to every downstream node.
- `./shanks doctor`'s Git/gh version check only guards a stale local dev
  machine; CI's `ubuntu-latest` always ships far newer versions, so the
  documented floor (Git 2.30, gh 2.40) is never actually exercised. Pinning
  old Git/gh versions in CI to prove the floor works is real setup effort for
  a small payoff — defer unless a real floor-version bug shows up.
- `critic_auditor` runs *before* `validation` in the graph (build -> critic
  -> validate), and `ClaudeOpus48CriticAdapter` has no `Bash` at all, so it
  can never actually run the tests it's judging - only reason from source.
  `GPT56LunaCriticAdapter` (`codex exec --sandbox read-only`) can execute
  commands read-only, so the two critics have materially different
  verification power. Worth a design discussion, not just a permissions
  tweak, before changing it.
- No network egress control on Ralph's build agent - the denylist only
  blocks the specific `curl|sh` pattern, nothing stops `pip install
  <package>` or other outbound calls. `scripts/sandbox_claude.sh` (the
  filesystem sandbox) deliberately leaves `(allow network*)` in its
  profile, since Claude itself needs network for its own API calls, so
  this would need per-host allowlisting (Anthropic's API, not arbitrary
  destinations), not a blanket deny. Defer until there's a concrete need
  (e.g. running against untrusted PRD content).
- No audit trail of what Ralph actually did inside a session - the run
  manifest records the launching command and the final `--print` output,
  not the individual tool calls (files read/written, Bash commands run)
  during the session. Would help post-incident review; capturing
  `--output-format stream-json` (or equivalent) into the run manifest is
  the likely shape.
- `scripts/sandbox_claude.sh` only sandboxes on macOS (`sandbox-exec`); it
  falls back to unsandboxed elsewhere. There's no separate "Windows" case
  to build - the whole toolchain (ralph.sh, hooks/*.sh, ./shanks) is
  bash-only, so a Windows user is already running it under WSL2, which is
  Linux. This is really one item: Linux sandbox parity (bubblewrap or
  Docker, scoped to $TARGET_DIR the same way). No urgency today since
  Ralph doesn't run in CI and local dev here is macOS; revisit if Ralph
  ever runs on a Linux/WSL dev box or in CI.
- `scripts/sandbox_claude.sh`'s write allowlist
  (`~/.claude`/`~/.codex`/`~/.npm`/`~/.cache`) was hand-picked by probing
  `claude --version`/`codex --version` empirically, not from upstream
  documentation - a future CLI version adding a new config/cache path
  would silently reintroduce "Operation not permitted" failures that look
  like flaky runs, not a sandbox problem. Consider a `./shanks doctor`
  check that runs `claude --version` (and `codex --version`) through the
  sandbox wrapper to catch that drift immediately instead of mid-run.
- The `Write|Edit` `PreToolUse` hooks disagree on fail-open vs fail-closed
  when `jq` is missing: `guard-dependency-files.sh` fails open (allows the
  write) so a missing `jq` doesn't block all edits, while `secret-scan.sh`
  (and `deny-dangerous.sh` on `Bash`) fail closed. That split was a
  deliberate call per-hook based on how safety-critical each one is, but
  it's not written down anywhere as a policy - worth a short note in
  `hooks/HOOKS.md` (or a repo convention) on when a new hook should pick
  which, so it's a decision and not just whatever the author of the next
  hook happens to do.
- `hooks/HOOKS.md` is a manually-maintained doc that's needed a hand-edit on
  every single hook change so far (which agents get which hook, matched
  against each adapter's `--tools` list) - nothing cross-checks its claims
  against the actual `--tools` strings in `workflow/adapters.py`, so it can
  silently drift the next time someone changes a tool list without
  remembering to update the doc. A small test asserting the documented
  tool-scope table stays consistent with `adapters.py` would catch that.
- `./shanks doctor`'s `tools` check only verifies `gitleaks`/`jq` are
  present, not their version (unlike `git`/`gh`, which have
  `_MIN_TOOL_VERSIONS`) - a `gitleaks` upgrade could silently change
  detection rules/behavior with nothing to notice. Low urgency; worth a
  version floor if a real detection regression ever traces back to a
  `gitleaks` upgrade.
- Lesson from `hooks/pr-checkpoint-reminder.sh` (built, then removed this
  session): before adding a new advisory `PreToolUse`/`PostToolUse` hook as
  a "safeguard" against an agent skipping a step, check that the failure
  mode is actually a tool-call boundary. Hooks can't see whether the agent
  chose prose over calling a tool at all - only tool calls that do happen.
  That hook's whole premise didn't hold up; worth checking this before
  building the next one.
- `workflow/cli.py`'s `_REQUIRED_TOOLS` (`./shanks doctor`) and
  `GitHubAdapter.preflight()`'s `required_tools` (`workflow/adapters.py`,
  extended to include `jq`/`gitleaks` in #40) are now two independently
  hardcoded tuples checking the same tool set, with no test asserting they
  stay in sync. A future tool addition to one and not the other would
  silently reopen the same "doctor says fine, run stalls anyway" gap #40
  just closed. Extract a shared constant or add a test asserting the two
  lists match.
- `dev/new features.txt` is tracked in git (`git ls-files dev/` confirms it)
  even though `.gitignore` has a blanket `dev/` pattern and `dev/context.md`
  says "because dev/ is ignored, it is not tracked or included in future
  PRs unless deliberately copied out" - that note is now inaccurate for
  this file specifically. Either deliberately untrack it and stop
  hand-editing roadmap state into it, or update `dev/context.md` to say
  this one file is a tracked exception, so the two docs stop disagreeing
  about whether roadmap edits belong in a PR.
- `_agent_environment()` (`workflow/adapters.py`) passes the entire parent
  shell environment through to the Bash-capable build agent except a 2-key
  blocklist (`GH_TOKEN`, `GITHUB_TOKEN`). Any other secret in the operator's
  shell (cloud credentials, unrelated API keys) is visible to the agent, and
  combined with the open network egress noted above, exfiltratable. Consider
  inverting this to an explicit allowlist of environment keys the agent
  actually needs.
- Both `subprocess.run(..., timeout=...)` call sites in `workflow/adapters.py`
  rely on Python's default `TimeoutExpired` handling, which only signals the
  direct child - a command invoked through a wrapper (`sandbox-exec`, a
  shell) can leave grandchild processes running past the deadline. Needs
  `start_new_session=True` plus killing the process group on timeout.
- `scripts/quality_gates.py`'s mypy target list only checks `adapters.py`,
  `contracts.py`, `retries.py`, and `state.py` - `nodes.py`, `lifecycle.py`,
  `workspaces.py`, `cli.py`, and `graph.py` (the largest and most stateful
  modules) are unchecked. Extend the list once those modules are clean under
  mypy, or budget time to fix what surfaces.
- Roadmap bookkeeping (removing/renumbering a completed item in
  `dev/new features.txt`) currently happens inside the feature PR that
  completes it, which caused the same kind of conflict as the point above
  when #42 and #43 both edited the Priority 1 header in parallel. Consider
  doing that edit as a separate follow-up commit to `main` after each PR
  merges instead of bundling it into the feature branch.

Deferred

- Parallelism and additional agent roles. Revisit after isolation, recovery,
  and pull-request lifecycle behavior are reliable.
